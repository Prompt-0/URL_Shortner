## 2024-07-29 - Prevent Information Disclosure in API Error Handling
**Vulnerability:** Raw database errors were being exposed to users via the API error responses in `src/api.rs`. For example, `internal(&format!("database error: {db_err}"))` would leak internal schema details or system state directly to the client when a database query failed.
**Learning:** Returning unmasked error messages provides attackers with valuable intelligence about the backend structure, such as database type, field names, or table schema, which can be exploited for further attacks.
**Prevention:** Internal application and database errors must be securely logged on the server side using the `tracing` crate (e.g., `tracing::error!("database error: {e}")`) while returning a generic, safe error message (e.g., "Internal server error") to the client. This approach ensures developers maintain visibility into failures without exposing sensitive information.
